# agent-radio 다음 단계

작성일: 2026-08-21
상태: OPEN
기준 커밋: `87df4ab` (origin/main)

## 이 문서가 답하는 것

오늘 origin/main 이 42커밋 전진했고, 그 과정에서 **무엇을 재려던 것인지가 두 번 바뀌었다.**
다음 사람이 같은 길을 다시 걷지 않도록 지금까지 확정된 사실과 남은 갈림길을 적는다.

## 확정된 사실 세 가지

### 1. 계획 협상은 이 과제군에서 차이를 만들지 않는다

24픽스처 · 루브릭 109항목 · 판정 218건을 가리고 채점한 결과다.

```
기본(협상 없음)   통과 99 · 실패 6
협상              통과 102 · 실패 3
갈린 항목          3개 (전부 협상 우세)
```

3/109은 차이가 아니라 차이의 부재다. 갈린 3개가 전부 같은 방향인 것이 유일하게
눈에 걸리지만, 같은 방향이 세 번 나올 확률은 25%다.

채점 기록은 `evaluation/agent_radio/records/*--*--2.json` 에 있다(`repeat=2`).
`repeat=1` 은 그 이전 채점이며 덮지 않았다.

### 2. 어제의 "협상 열세"는 모델이 아니라 루브릭이었다

같은 모델로 13:16(협상 열세) → 102:99(협상 우세)로 뒤집혔다. 바뀐 것은 계측기다.
루브릭 112항목 중 22개가 목표에 없는 것을 요구했고, 잘못된 판정 12건 중 7건이
협상 쪽에 불리하게 몰려 있었다.

**단, 그 스윕은 고친 협상 프롬프트를 읽지 않았다.** 픽스처가 `201d43e` 에 고정돼
있어 프롬프트 수정 4커밋이 트리에 없었고, 채점을 다 끝낸 뒤에 발견했다. 자세한
내용은 [[pag-eval-pinned-source]] 와 커밋 `148a3ce` 에 있다.

### 3. 워커 간 쪽지는 작동하지만 완료 보고로 쓰인다

관측된 쪽지 7건이 **전부 워커 → 리드**다. 워커끼리는 0건.

원인을 세 개로 좁혔다.

- **(고쳤음, 부분적)** 로스터가 `라벨 → 이름` 만 보여 줘 워커가 동료의 담당을
  몰랐다. 담당을 실었더니(`b125268`) 워커가 "team_model_operations.py 는 W-02
  범위" 처럼 경계를 인식했다 — 정보는 도달했다. **그래도 수신자는 리드였다.**
- **(미해결, 가장 근본적)** cycle 당 열린 model operation 이 하나뿐이라 워커가
  동시에 돌지 않는다. 순차면 뒤에 도는 워커가 앞선 워커의 파일을 읽으면 되므로
  물을 일이 없다. 작업 폴더도 공유된다.
- **(미검증, 가장 싸다)** 워커 계약이 "쪽지는 아무 라벨에게나 보낼 수 있다" 고만
  말하고 **언제 리드 대신 동료에게 보내야 하는지는 말하지 않는다.**

## 오늘 예측이 깨진 것 — 다시 봐야 하는 결론

`--workers 2` 를 주면 계획이 **3태스크 · 2담당** 으로 갈린다. 시도한 모든 픽스처에서
그랬다.

그러면 "협상 계획의 60%가 태스크 1개" 는 픽스처의 한계가 아니라 **워커 1명 조건의
성질**이다. 거기서 끌어낸 결론 — "이 픽스처들로는 협상을 잴 수 없다" — 은 워커 2명에서
다시 검증해야 한다. 태스크가 셋이면 `overlap` · `dependency_conflict` · `scope` 가
발동할 표면이 생긴다.

**이것이 가장 값싸고 가장 큰 미확인 항목이다.**

## 갈림길

### A. 협상을 워커 2명에서 다시 잰다 — 권장

무엇을 바꿀 필요도 없다. 이미 있는 24픽스처를 `--workers 2` 로 협상 켬/끔 두 조건에
돌리면 된다. 위 "예측이 깨진 것" 이 사실이면 결과가 달라질 수 있고, 아니면 협상에
대한 판단이 확정된다.

전제: 병렬화(아래 C). 48칸을 순차로 돌리면 8시간이다.

### B. 쪽지 수신자 유도 — 싸고 되돌리기 쉽다

워커 계약에 "동료가 필요할 사실은 리드가 아니라 그 동료에게 보내라" 를 한 줄
추가하고 두 조건으로 비교한다. 실패해도 한 줄이다.

주의: 이것으로 쪽지가 동료에게 가더라도 **순차 실행이라 받은 쪽이 이미 파일에서 알 수
있는 정보**일 가능성이 크다. 그 경우 "쪽지가 왔다" 와 "쪽지가 값이 있었다" 는 다르다.

### C. 스윕 병렬화 — 유료 호출 없음

지금 `only_one_run` 이 동시 실행을 거부하는 이유는 provider 경합이 아니라 **런 산출물이
저장소 안에 쓰이는 것**이다. 한 런의 산출물이 다른 런의 전후 스냅샷 사이에 떨어져
격리 검사가 "누구도 만들지 않은 변경" 을 보고한다(`runner.py` 의 `only_one_run`
docstring).

산출물을 저장소 밖에 쓰고 끝난 뒤 복사하면 락을 풀 수 있다. 확인해야 할 것 셋:
LMG 가 동시 세션을 견디는가, SQLite 동시 쓰기, 그리고 비용은 줄지 않는다는 점(시간만
줄어든다).

50칸이 8시간 → 2~3시간.

### D. cycle 당 동시 연산 허용 — 크고 위험하다

쪽지의 원래 그림(동료에게 물어보기)이 성립할 유일한 길이지만, `reserve` 의 사전 검사와
부분 유일 색인 `idx_team_model_operations_one_open_cycle` 이 강제하는 불변식을 건드린다.
복구·재개 경로가 전부 "열린 연산은 하나" 를 전제한다. 설계 결정이며 이 문서의 범위가
아니다.

## 미해결로 남긴 결함

- **I4 (최우선)**: 쪽지 접두가 공간 정책 블록이 없는 프롬프트에도 붙는다 — 모든 repair

  스펙 결정이다(stage 로 주입을 제한해 전달을 잃거나, 그 네 프롬프트 빌더에 정책을
  실어 나르거나). **덧붙이기는 답이 아니다** — 정책 없는 프롬프트에서는 쪽지에 마지막
  말을 주는 셈이다.
- **I2**: 메시지 id 만 고정되고 렌더된 접두는 고정되지 않는다. 배포 후
  `roster_block`/`radio_block`/`WORKER_PROMPT` 문구를 바꾸면 재개하는 prepared 런이
  전부 깨진다.
- **유실 0의 검증된 예외**: `apply_worker_outcome` 커밋과 쪽지 기록 사이 창이
  in-process 도 크래시도 닫지 않는다. 닫으려면 재조정 스윕이 필요하다.
- **결과 계약 기준의 내용 드리프트**: radio-lite 가 `TaskOutcome` 에 `mentions` 와
  `mention_refusals` 를 추가했다. 채점 기준 중 "결과 계약의 키는 이것뿐" 이라고 단정한
  것은 줄이 밀린 것이 아니라 **내용이 거짓**이 됐을 수 있다. 표본 하나는 확인했고
  무해했으나(`mentions` 는 `verifications` 의 형제), 다음 채점 전에 결과 계약 관련
  기준을 다시 봐야 한다.
- **`provider_protocol_error`**: 144런 중 11건(7.6%)에서 호출 도중 원격이 끊긴다.
  제품은 `ambiguous` 로 멈추는 것이 옳고, 스윕은 재시도로 흡수한다. 근본 원인은 LMG
  쪽이며 파지 않았다.
- **루브릭 결함 1건**: `impact-of-trusting-a-worker-computed-check-result` R3 은 두 요구
  중 하나를 포기하라고 요구하는데, 두 모델이 독립적으로 **둘 다 지키는 제3의 길**을
  찾았다(실행 결과를 워커의 텍스트가 아니라 플랫폼 실행 경계에서 포착해 검사에 바인딩).
  항목이 불필요한 양보를 요구한다. 양쪽이 같이 실패했으므로 비교는 왜곡되지 않았다.

## 다시 밟지 말아야 할 함정

- **픽스처의 `repo_ref` 를 올리지 않으면 고친 코드를 재지 않는다.** 프롬프트나 `src/`
  를 고친 뒤 스윕 전에 확인하라. 올릴 때는 기준의 줄 인용을 **내용 기준으로** 옮겨라
  (스크래치패드 `remap-lines.py`). 커밋 해시는 손으로 쓰지 말고 `rev-parse` 로 읽어라 —
  틀린 해시로 `git show` 가 조용히 실패해 재매핑이 아무것도 하지 않았다.
- **루브릭 항목을 지우면 기준 번호가 밀린다.** 항목에 `id` 필드가 있으므로 위치가
  아니라 그것으로 맞춰라. 개수 일치를 검사로 걸어 두는 것이 최소 방어선이다.
- **채점 기록 파일명은 `<픽스처>--<팔>--<repeat>.json` 이다.** 같은 `repeat` 으로 쓰면
  기존 기록을 덮는다. 이전 판정은 증거이므로 새 회차는 번호를 올려라.
- **exit 0 은 "돌았다" 일 뿐 "답했다" 가 아니다.** 러너는 의도적으로 실패한 런에도 0을
  준다. 산출물의 `error`/`summary` 를 읽어라. `sweep.sh` 가 이미 그렇게 한다.
- **프로세스를 명령줄로 찾아 죽이지 말라.** 찾는 명령 자신이 매칭돼 자기 셸이 죽는다.
  `sweep.sh` 가 자기 PID 를 `<로그>.pid` 에 남긴다.

## 2026-08-23 추기 5 — F 실행: 자문이 실제로 작동했고 E는 필요 없다

F 를 두 판 돌렸고, 첫 판이 두 번째 판의 설계를 결정했다.

### F1 — 실패했고, 그 실패가 진짜 장벽을 알려줬다

`agree-on-a-name-nobody-has-written-yet`: 두 파일이 정해지지 않은 이름 하나를
공유해야 하고 서로를 읽는 것이 금지된 과제. 동시 실행됐고 이름도 일치했지만,
**워커가 조율한 것이 아니었다.** 리더가 계획 단계에서 이름을 골라 두 태스크 설명에
박아 넣었다: `CHECK_KIND = "byte-limit-v1"` 이 양쪽 description 에 그대로 있었다.

**이 구조에서 리더의 계획이 곧 조율 수단이다.** 목표가 열어 둔 것은 리더가 태스크
설명을 쓰는 순간 닫히므로, 워커에게는 물어볼 것이 남지 않는다. 쪽지 채널을 아무리
개선해도(E) 쓰이지 않는다 — 문제가 채널 아래가 아니라 위에 있었다.

### F2 — 리더에게 정하지 말라고 하면 자문이 발동한다

`agree-without-the-lead-deciding`: 같은 과제에 **"리더는 이름을 고르지 마라,
후보를 적는 것도 금지"** 를 넣었다. 리더는 지시를 지켰고, 대신 계획에
"고른 값을 W-02 에게 직접 알려라" / "W-01 에게 정확한 값을 물어라" 를 적었다.

관측된 전체 흐름(런 completed, 4.9분):

```
worker_execution  W-01  03:35:35 ─── 03:36:43   ┐ 겹침
worker_execution  W-02  03:35:35 ─── 03:36:17   ┘
consult_peer      W-01  03:37:38 ─── 03:37:43   ← 동료가 답했다 (리더 아님)
mediation_worker  W-02  03:37:44 ─── 03:38:20   ← 답을 받아 재개
```

주고받은 내용:

```
[자문] W-02 → W-01: What exact literal CHECK_KIND string did you choose?
[자문] W-01 → W-02: I chose the literal "size_limit" in src/size_check.py (CHECK_KIND at line 6).
```

결과물: `CHECK_KIND = "size_limit"` 과 `REGISTRY = {"size_limit": "size"}` — **일치**.
쪽지 4건 전부 워커간이며 **전부 배달됐다**(F1·추기 4 의 배달 0건과 대비).

### 결론

- **동료 자문(consult_peer)은 작동한다.** 작업 중간에 동료에게 묻고, 동료가 자기
  세션 기억으로 답하고, 물은 쪽이 그 답으로 일을 마쳤다. 이것이 이 실험군이
  처음부터 재려던 협업이다.
- **E 는 필요 없다.** E 가 주려던 것(작업 중간 통신)은 자문 경로가 이미 준다.
  쪽지(mentions)가 턴 끝에만 나가는 것은 사실이지만, 그것은 쪽지의 용도(전달·통보)에
  맞고, 중간에 답이 필요한 경우는 자문이 담당한다.
- **자문이 발동하려면 리더가 결정을 워커에게 남겨야 한다.** 이것이 남은 실질적
  레버다: 프롬프트가 리더에게 "네가 정할 수 있는 것은 정하라" 고 말하는 한, 대부분의
  과제에서 동료 간 통신은 잉여다. 다음에 물어볼 것은 "리더가 덜 정하는 것이 결과를
  좋게 하는가" 이며, 그것은 채널 문제가 아니라 계획 프롬프트 문제다.

## 2026-08-23 추기 6 — 대조군: 리더가 이미 중계기다. 실험군의 답.

추기 5 의 F2 에는 대조군이 없었다. 자문이 발동해 이름이 일치한 것은 봤지만
"쪽지가 없었어도 됐는가" 에는 답하지 못했다. 같은 픽스처
(`agree-without-the-lead-deciding`)를 **쪽지 끄고**(legacy) 동시 실행으로 2회 돌렸다.

**둘 다 이름이 일치했다.** 그리고 어떻게 일치했는지가 이 실험군의 답이다.

```
ctrl1  04:13:15  agent_output  "Implemented size checker with shared kind name file_size."
       04:13:44  query         "What exact CHECK_KIND string did you choose for src/size_check.py?"
       04:13:49  answer        "The chosen CHECK_KIND string is \"file_size\"."   ← 리더가 답했다
       → REGISTRY = {"file_size": "size"}        CHECK_KIND = "file_size"     일치
ctrl2  → REGISTRY = {"size_limit": "size"}       CHECK_KIND = "size_limit"    일치
```

워커는 쪽지 채널이 없어도 `needs_info` 로 물었고, **리더가 답했다.** 리더가 답을
알 수 있었던 이유는 mediation 프롬프트가 `_collect_outputs()` 로 **완료된 태스크
결과**를 담고 있고, W-01 이 자기 요약에 고른 이름을 적었기 때문이다
("...with shared kind name file_size"). 리더는 그것을 읽어 중계했다.

### 결론 — 동료 간 통신은 이 아키텍처에서 잉여다

- **필요는 실재한다.** 두 워커는 공유 결정을 조율해야 했고, 실제로 물었다.
- **그 필요는 이미 채워져 있었다.** 리더가 중계기로 동작한다. 쪽지·자문이 하는 일을
  리더 경유 `query`/`answer` 가 같은 비용(왕복 1회)으로 한다.
- **자문의 고유 능력은 관측되지 않았다.** 자문만 할 수 있는 것은 "동료가 **아직 일하는
  중**일 때 답을 받는 것"인데, F2 에서도 대조군에서도 묻는 시점에 상대는 이미
  끝나 있었다. 워커들이 비슷한 시간에 끝나고 질문은 자연히 그 뒤에 오기 때문이다.
- 따라서 **쪽지·자문이 결과를 바꾼 사례는 이 실험군에서 하나도 없다.** 기능은
  작동하고(구현·테스트·라이브 검증 완료) 값은 확인되지 않았다.

### 이 실험군에서 값이 확인된 것 하나: 동시 실행

같은 픽스처가 순차 11분대 → 동시 4.9~6.9분. 프로바이더 호출이 겹치는 만큼 그대로
줄고, 쪽지와 무관하게 얻어진다. **동시 실행은 쓰고, 동료 통신은 켜 둘 이유가 약하다**
가 지금까지의 측정이 지지하는 결론이다.

### 남긴 것

- 되돌리지 않았다. 쪽지·자문·동시 실행 모두 플래그 뒤에 있고 기본값은 보수적이다
  (`team_peer_messages_enabled` 는 기존대로, `AGENT_TEAM_CONCURRENT_WORKERS` 는 꺼짐).
  값이 없다는 것은 해가 있다는 것과 다르고, 리더 중계가 막히는 조건(리더 세션이
  결과를 못 보는 경우 등)이 나오면 자문이 그 자리를 메운다.
- **계획 프롬프트 A/B(리더가 덜 정하기)는 하지 않기로 했다.** 그 실험의 전제는
  "동료 통신이 값을 만든다" 였고, 대조군이 그 전제를 부정했다. 리더가 덜 정하면
  조율 왕복만 늘고 결과는 같다 — F1(리더가 정함, 왕복 0) 대 F2(리더 금지, 자문 왕복
  1회)에서 이미 그 방향이 보였다.
- 다음에 값이 있을 만한 것은 이 실험군 안이 아니라 **실제 업무에 팀 런을 써 보는
  것**이다. 지금까지 모든 측정이 자기 저장소로 자기를 측정했고, 동시 실행의 속도
  이득은 실제 과제에서야 의미가 드러난다.
