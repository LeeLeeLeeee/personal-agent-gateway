# DashboardView 컴포넌트 분석

## 요약

- Root: `frontend/src/components/organisms/DashboardView/index.jsx`
- Modes: `api-state,test`
- Verdict: 기존 Dashboard organism에 provider 계정 한도 window 렌더링을 추가하는 것이 적절하다. 새 공유 컴포넌트는 필요 없다.

## Props 흐름

| Prop | 출처 | DashboardView에서의 역할 |
| --- | --- | --- |
| `onOpenTarget` | `GatewayApp` | operation row의 `target`을 parent 화면 전환 callback으로 전달한다. |
| `onRelogin` | `GatewayApp` | operations API가 재로그인을 요구할 때 parent의 인증 흐름을 실행한다. |

`ProviderUsageCard`는 parent prop이 아니라 `report.providers`의 각 항목을 내부에서 받는다. Task 3이 추가한 `rate_limits`는 이 local card boundary에서만 소비해야 하며, DashboardView가 provider 상태를 다시 해석하면 안 된다.

## API / 상태 추적

| State/effect | 입력 | 역할 및 결과 |
| --- | --- | --- |
| `report`, `error`, `loading`, `reloadKey` + 첫 `useEffect` | `reloadKey` | `api.dashboardUsage()`를 호출한다. 성공 시 provider usage report를 보존하고, 실패 시 usage 영역에 retry UI를 보인다. cleanup의 `active` guard가 unmount 뒤 state 변경을 막는다. |
| `operations`, `operationsError`, `operationsLoading`, `operationsReloadKey` + 둘째 `useEffect` | `operationsReloadKey` | `/api/operations` 응답을 `isOperationsPayload`로 검증한 뒤 `operationsDashboardModel`에 넘긴다. usage 실패와 독립적이다. |
| `apiErrorAction` | operations error | `OperationsDashboard`에서 오류가 401 계열이면 `onRelogin`, 그 외면 operations reload를 선택한다. 이 결정은 usage retry와 독립이다. |
| `operationsDashboardModel` | validated operations payload | active item, attention item, health/system attention을 계산해 `OperationRows`와 `SystemStatus`가 소비할 UI model을 만든다. |
| `sessions`, `sessionsLoading`, `sessionsError`, `lmgStatus`, `sessionsReloadKey`, `showAllSessions` + 셋째 `useEffect` | `sessionsReloadKey` | `/api/dashboard/sessions`의 LMG 상태와 session 배열을 분리해 처리한다. LMG가 non-ready일 때 session empty 상태를 표시하지 않는다. |
| `providers` | `report?.providers || []` | usage card 목록의 단순 파생값이다. provider 가용성은 backend response 그대로 사용한다. |
| `visibleSessions`, `hiddenSessionCount` | `sessions`, `showAllSessions` | 최초 5개 session만 보여주고 더보기 버튼으로 전체를 전환한다. |

Provider 한도 window는 Task 3에서 `src/personal_agent_gateway/local_usage.py`의 `ProviderUsage.rate_limits`로 정의되고 `src/personal_agent_gateway/api/dashboard.py`의 `/api/dashboard/usage` response에 포함되는 planned contract다. 현재 frontend는 legacy `usage.used`/`usage.weekly_limit`만 읽으므로, 이번 source 변경은 `rate_limits: [{ window_minutes, used_percent, resets_at }]`을 이 existing effect의 `report`에서 소비하도록 바꾼다. 사용자 새로고침은 `reloadKey`를 증가시켜 LMG의 on-demand 수집을 다시 트리거하며, operations/session 요청을 함께 재실행하지 않는다.

## 외부 의존성

- React `useEffect`/`useState`: 세 remote resource의 loading/error lifecycle을 독립적으로 유지한다. rate-limit UI는 새 fetch state를 만들지 않고 existing usage effect를 재사용해야 한다.
- Shared `api` client: 브라우저 fetch와 HTTP 오류 정규화를 담당한다. DashboardView는 endpoint URL이나 Bearer token을 직접 다루지 않는다.
- `StatusBadge`: usage가 아닌 operations 상태의 표현 leaf다. provider rate-limit gauge가 이 atom의 상태 vocabulary를 재사용하면 의미가 섞이므로, 현재 usage CSS/ARIA 패턴을 유지하는 것이 맞다.

## 테스트 현황과 회귀 위험

| 현재 테스트 | 보장하는 흐름 | 이번 변경과의 관계 |
| --- | --- | --- |
| `calls the dashboard usage API and renders provider usage as a card and gauge` | weekly legacy fields와 하나의 progressbar | `rate_limits` 배열의 여러 window gauge로 교체되는 직접 회귀 지점이다. |
| `shows uncollected and unavailable providers without inventing a gauge` | unconfirmed/unavailable에 gauge를 만들지 않음 | LMG 미수집 시 `rate_limits: []`을 동일한 no-data state로 다뤄야 한다. |
| usage/operations retry tests | usage 재시도는 operations와 독립 | rate-limit refresh도 같은 `reloadKey` 경로를 사용해야 한다. |
| `operationsModel.test.js` | payload validation과 active/attention 분류 | account-limit renderer가 operations view-model의 분류 규칙을 변경하지 않아야 한다. |
| operations rendering/empty-state tests | active work, health, attention, operations empty state | account-limit renderer가 operations model이나 `StatusBadge` wiring을 바꾸지 않아야 한다. |
| local sessions rendering test | session table row의 provider/model/storage metadata | account limits가 sessions API payload와 별도임을 유지해야 한다. |
| five newest sessions/더보기 test | 처음 5개 제한과 hidden count expansion | usage card 변경이 session list state에 영향을 주지 않아야 한다. |
| four non-ready LMG state cases | unreachable, unauthorized, not_ready, protocol_error session messages | account-limit 미수집은 session endpoint의 LMG status UI를 덮어쓰지 않아야 한다. |
| session/Lmg status tests | session endpoint의 LMG 오류 처리 | account-limit 수집 실패와 session LMG 상태를 섞지 않아야 한다. |

추가 RED 사례: Codex provider가 300분과 10080분 두 window를 반환할 때 각각 `aria-valuenow`를 가진 progressbar와 `5시간`/`7일` label이 렌더링되는지 확인한다. 해당 card가 `로컬 실행 횟수`나 legacy `주간 한도`라고 표현하지 않는지도 확인한다.

## 권장 후속 작업

1. `ProviderUsageCard` 내부에서 `rate_limits`를 map해 각각의 accessible gauge를 렌더링한다. 이유: API data boundary가 이미 card prop에 있고, parent state/effect를 건드릴 필요가 없다.
2. 기존 legacy numeric weekly fields의 gauge/metric branch는 account limit window renderer로 바꾼다. 이유: backend가 실제 계정 한도를 window percent로 전달하므로 두 semantic model을 한 카드에 섞으면 오해를 만든다.
3. `DashboardView.test.jsx`에 다중 window 및 빈 `rate_limits` RED regression을 추가한다. 이유: 기존 test는 단일 weekly quota만 다룬다.
